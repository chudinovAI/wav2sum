# PLAN: CHU-107 — переехать с Ollama на mlx-lm

Сейчас LLM (чистка и перевод диктовки, summary звонка) живёт в отдельном процессе Ollama. `llm.py` — тонкая обёртка над `ollama.Client`: класс `LLM` с `chat(system, user, examples)` и `unload()`. Его создают `dictation.py` (gemma4 e4b, `keep_alive="10m"`, `timeout=30`), `daemon.py` (summary, gemma4 12b, `think=True`, `keep_alive="1m"`, если модели разные) и `cli.py` (summary для `wav2sum meeting.mp3`). `daemon._llm_memory_mb()` спрашивает у Ollama `ps()`, это уходит в `status` → меню и TUI.

Цель (по ответам Андрея): быстрее и без Ollama. Модель в памяти держится не дольше, чем сейчас: та же логика `keep_alive`, только своя.

## Решения

- **Зависимости.** Добавить `mlx-lm`, убрать `ollama`, поднять `transformers` до `>=5` (`mlx-lm` 0.30+ требует transformers 5). Lock собирается, тесты на Linux проходят (118/118), но настоящую загрузку GigaAM, pyannote и speechbrain тесты не проверяют — это руками на Mac.
- **Модели.** Те же gemma4 в MLX: e4b QAT 4bit для диктовки, 12b QAT 4bit для summary (коллекция `mlx-community` Gemma 4 QAT). Точные имена репозиториев проверить на Mac при первой загрузке. В `config.toml` имена меняются на репозитории Hugging Face.
- **Память, как сейчас.** Модель грузится при первом `chat` и выгружается после простоя: диктовка через 10 минут, summary через 1 минуту (или сразу, если это CLI). Таймер сбрасывается на каждом вызове. Если модели диктовки и summary совпадают — один экземпляр, как сейчас `shared`.
- **Параллельность.** Один lock вокруг генерации. Диктовка во время summary ждёт текущий запрос summary. Шедулер не делаем.
- **Протокол не меняется.** `llm_memory_mb` считаем из mlx (`mx.get_active_memory()`); Swift и TUI не трогаем.
- **Уходит.** `timeout=30`, `client()` с `trust_env=False`, `ollama pull` в README, Ollama в CLAUDE.md и SPEC.md.

## Как это ложится на остальные задачи

- **CHU-97 (ASR на ANE).** Цель эпика — чтобы ASR диктовки не делил GPU с Gemma, пока та пишет summary. После CHU-107 Gemma живёт в том же процессе, что и ASR, и делёж GPU виден в коде, а не спрятан в Ollama.
- **CHU-101 (lock на вычислитель).** Lock LLM из этой задачи и есть будущий «GPU-lock» для MLX. Сейчас он отдельный от `Models._lock`, чтобы не поменять поведение до CHU-100. В CHU-101 их сведём по устройствам.
- **CHU-98 (Core ML конвертация GigaAM)** пойдёт уже на transformers 5, поэтому апгрейд лучше сделать сейчас, а не посреди эпика.
- **Prompt cache** для системного промпта диктовки — главный рычаг задержки после переезда, но живёт только пока модель загружена. Отдельной задачей после CHU-107, если замер покажет, что нужно.

## Шаги

1. **transformers 5.** `pyproject.toml` + `uv.lock`. Проверка: `uv run pytest --cov`; руками на Mac — диктовка по-русски и по-английски, обработка записи звонка с диаризацией.
2. **`llm.py` на mlx-lm.** Сначала тесты в `tests/test_llm.py` (mlx-lm подменён): `chat` собирает те же сообщения с примерами, передаёт температуру и `enable_thinking`; ответ без блока размышлений; модель грузится один раз при первом вызове; после простоя `keep_alive` выгружается, следующий вызов грузит снова; `unload` освобождает; два `chat` из разных потоков не идут одновременно. Потом код.
3. **Демон и CLI.** Тесты в `tests/test_daemon.py`: `llm_memory_mb` из mlx; при `shared` один экземпляр. Потом код: убрать `client`, Ollama-`_llm_memory_mb`.
4. **Конфиг, README, SPEC.md, CLAUDE.md.** Новые имена моделей по умолчанию, убрать `ollama pull`.
5. **Руками на Mac:** диктовка, перевод, команда, summary звонка; время ответа и память в меню до и после; через 10 минут простоя память LLM уходит в 0.

Проверка каждого шага: `uv run pytest --cov` (≥ 80 %), `uv run ruff check && uv run ruff format --check`.
